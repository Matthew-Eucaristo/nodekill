Reclaim what Node.js leaves behind.
Safely, and the official way.

Every project grows a node_modules, a .next, a build folder. Every package manager keeps a cache. Every npx run, global install and Node version stays. nodekill finds all of it, shows what each one really frees and why it is safe or not, and removes only what you pick. Folders go to the Trash; caches, global packages and Node versions go through their own tool's command.

What it finds

Not just node_modules. The whole footprint.

In projects, a folder counts only at its exact place next to the file that proves its tool is used, never by name alone. On the machine, each item is removed only by its owner's command, which nodekill runs from your home folder. Every rule links its source in docs/rules.md.

Safety model

It refuses anything it cannot verify.

Every item gets one of four levels and the evidence behind it. The same four badges as the rest of the family, so a glance tells you what a key will touch.

● safe

Rebuildable, git-ignored with nothing tracked inside, project idle 7+ days, nothing running in it.

s takes these in projects, a everywhere. Empty folders are skipped.

▲ review

  • the project changed this week
  • no lockfile, so a reinstall may differ
  • git ignores the project folder itself
  • files in node_modules changed after the install
  • the output may be what you deploy
  • a linked worktree an agent may still use
  • a global tool or Node version you installed on purpose

Allowed when you pick it. Never bulk-selected.

■ protected

  • git tracks files inside, or does not ignore it
  • a generic name such as dist outside a repository
  • it holds your data, or another repository
  • its tool is missing
  • the cleanup would empty a top-level folder of home
  • the Node you run, a default, npm, corepack

Shown, never removed.

◉ live

A dev server, build, test runner or the package manager is working in it right now.

Nothing is allowed until it stops.

⎔Pinned to what you saw

Right before acting, nodekill reads the item again and refuses it if anything safety-relevant changed since the scan: path, folder identity, git evidence, level, reasons, command.

⌘The official way only

Commands run by absolute path with a fixed argument list, never through a shell. The one exception is nvm, a shell function: nodekill sources its own nvm.sh and passes the version as an argument.

↯No symlinks, no surprises

The target must still be a real directory at its catalog position. Symlinks are never followed or removed through.

⌫Trash by default

Folders go to the Trash. --permanent deletes instead and turns the header red. Official commands delete by design, so the confirmation lists them apart.

◌Read-only modes

--dry-run, --list, --json and scan never remove anything. --yes takes safe project items only.

∅Quiet questions

To find caches it asks your tools read-only questions such as pnpm store path, with their prompts, update checks and downloads turned off.

How sizes are counted

What du says is not what you get back.

Sizes are allocated blocks, like du, with hard-linked files counted once. pnpm and Bun install from a global store: on macOS they clone files (APFS copy-on-write), and on Linux pnpm hard-links them. So nodekill asks APFS for each file's private size, and shows a FREES column when much of an item is shared.

  • Measured, never assumed. After acting, freed space comes from the disk's free space, before and after.
  • The Trash frees nothing until you empty it, and the receipt says so.
  • The bar shows both. Its coloured part frees space now; the cyan part goes only when its store is pruned.

Use and automate

A TUI when you look. A contract when you script.

In the TUI, enter shows exactly what will happen and asks first. tab groups by project, framework or idle time, o sorts, / filters and ? explains every colour and key. It fits 60 columns, and NO_COLOR turns colour off.

# interactive; scans ~/dev (else the current folder)
nodekill
# other roots
nodekill ~/work ~/side
# interactive, but nothing changes
nodekill --dry-run
# plain table, read-only
nodekill --list
# headless: trash safe artifacts of projects idle 30+ days
nodekill --older-than 30d --yes
# machine-readable, read-only (--ndjson streams)
nodekill scan --json
# act on ids + fingerprints; each item is re-checked
nodekill apply --plan plan.json
Exit codes

1error before acting
2usage error, or an invalid plan
3something was refused, nothing failed

Every item carries its id, a fingerprint of its safety-relevant state, sizes, evidence and the exact command. Paths are home-relative. The format is described in docs/contract.md and shared with the rest of the family.

Works alone, or under decruft. decruft, the family's umbrella, reads nodekill scan --json for its Node.js row and hands removals back through apply --plan, so nodekill re-checks every item with its own rules. fell and flutterkill speak the same contract.

Install

One binary. No Node.js of its own.

$brew install matthew-eucaristo/tap/nodekill

Recommended on macOS and Linux. Also installed for you by brew install matthew-eucaristo/tap/decruft.

$go install github.com/Matthew-Eucaristo/nodekill@latest

Needs Go 1.26 or later.

Download from GitHub Releases →

Archives for macOS, Linux and Windows on amd64 and arm64, with checksums.txt.

macOSfirst-class: sizes account for APFS clones, the Trash supports Put Back, running processes are checked with lsof.
Linuxfreedesktop Trash, /proc process checks, hard-link-aware sizes.
Windowsbest effort: the Recycle Bin, no running-process check, so nothing is bulk-selected.
Uninstalling leaves nothing behind 
brew uninstall nodekill
brew autoremove                     # removes Go if it was installed only to build nodekill
brew untap matthew-eucaristo/tap    # only if nothing else is installed from this tap

nodekill writes no configuration, cache, log or state anywhere. With go install: rm "$(go env GOPATH)/bin/nodekill". Anything it moved to the Trash stays there until you empty it or put it back.

Questions

Fair questions.

Why not just rm -rf node_modules, or npkill?

For one project's node_modules, that works. nodekill is for everything else too: framework caches matched next to the file that proves their tool, package-manager stores pruned by the package manager, npx entries, global packages and Node versions removed by their own tool. It checks git before touching a project folder, refuses what it cannot verify and shows what each item really frees. npkill's interaction model inspired the TUI.

Will it break a project?

A safe project item is rebuildable, git-ignored with nothing tracked inside, in a project idle for a week or more, with nothing running in it, and the detail pane says how it comes back (npm ci, pnpm install, next build). Anything without a lockfile, recently changed, possibly deployed or locally patched is marked review and never bulk-selected.

Why does a pnpm node_modules free almost nothing?

Because its files are clones (macOS) or hard links (Linux) of the pnpm store. Removing the folder frees only what is not shared; the space comes back when pnpm store prune drops packages no project references. nodekill shows that in the FREES column instead of promising the du number.

Does it need Node.js, or send anything anywhere?

No. It is a single Go binary. It never contacts the network itself, and the tools it asks run with update checks and downloads turned off. This page loads nothing from third parties either.

Will it remove the Node version I am using?

No. The Node on your PATH and each manager's default are protected, as are npm and corepack. Other versions are review items, with a note when a project under the scanned folders pins them.

Can I run it from a script or CI?

Yes. nodekill --older-than 30d --yes moves the safe artifacts of projects idle 30 days or more to the Trash and never touches caches, global packages or Node versions. For anything else, scan --json and apply --plan pass ids and fingerprints, and exit codes say what happened.

I found a bug that touches the wrong thing.

That is a security issue. Please report it privately through GitHub Security Advisories, not a public issue.
